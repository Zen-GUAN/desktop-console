# 修复记录：亮度卡片误报「不支持 / 此显示器未开放 DDC/CI」

> 2026-11-07 · 执行方：ZCode（后端） · 前端（Kimi 职责范围）**零改动**
> 本文件原计划写成交给 Kimi 的前端修复任务书；取证后发现根因在后端（ZCode 职责范围），按分工由 ZCode 直接修复，转为修复记录归档。

## 结论（一句话）

v2 亮度卡片误报「不支持」的根因是**后端** `Server.ps1` 的 `Get-MonitorState` 用 `return ,$result` 把数组多包了一层，`/api/state` 输出 `"monitors":[[{…}]]` 双层嵌套；前端拿到内层数组后 `.supported` 为 undefined，忠实渲染出「不支持」。**后端取值本身一直正常。**

## 推翻旧结论的教训

旧记录（2026-11-06）称「后端调用成功（ok=True cur=23），问题在前端，别再查后端」。该结论只验证了**亮度值**，没有验证 **JSON 形状**——形状也是后端的产出。此后查后端接口问题，值和形状都要看。

## 证据链（2026-11-07 实测）

1. 诊断日志（`%TEMP%\WinCtlPanel2-diag.log`）：`Monitors.Count=1, GetMonitorBrightness ok=True min=0 cur=23 max=100` → 取值正常
2. 修复前 `/api/state` 实测 JSON（起 `-NoBrowser` 服务 + token 直调）：

   ```json
   "monitors": [ [ { "index": 0, "supported": true, "percent": 23, … } ] ]
   ```

   双层嵌套。前端 `app.js` 的 `selectMonitor`（app.js:102-117）执行 `state.monitors[0].supported` → 内层数组上该属性为 undefined（falsy）→ `slider.disabled=true`、显示「不支持」「此显示器未开放 DDC/CI」。前端逻辑本身无错。
3. 根因代码（Server.ps1）：`Get-MonitorState` 结尾 `return ,$result`（逗号包裹防展开）+ `Get-State` 调用方 `monitors=@(Get-MonitorState)` → 嵌套存活并进 JSON
4. 修复后 `/api/state` 实测：

   ```json
   "monitors": [ { "index": 0, "name": "Generic PnP Monitor", "supported": true, "percent": 23, "raw": 23, "min": 0, "max": 100 } ]
   ```

   平铺 ✓ —— 前端无需任何改动即可正常渲染滑杆。

## 改动清单（全部在 `v2-web\server\Server.ps1`）

| # | 位置 | 改动 | 性质 |
|---|---|---|---|
| 1 | `Get-MonitorState` | `return ,$result` → `return $result` | **本 bug 真凶** |
| 2 | `Get-PhysMonitors` 失败路径 | `return ,$list` → `return $list` | 同类隐患：原来空列表会变成 `[[]]`，触发与真 bug 同样的「不支持」误渲染 |
| 3 | SelfTest | `$mons=@(Get-PhysMonitors)` 稳定为数组；新增「状态 JSON 形状」回归项（monitors 首元素必须是 PSCustomObject） | 防再犯 |
| 4 | SelfTest | 「无外链资源」检查排除 SVG xmlns（`http://www.w3.org/2000/svg` 是命名空间标识符，不发网络请求） | 修误报 |

## SelfTest 现状：17/18

唯一 FAIL：`DDC 失败可识别 · 零句柄返回 null` —— 本机显示器驱动**连句柄 0 都能成功读亮度**（诊断日志里物理显示器句柄本来就是 0），该测试「零句柄必失败」的假设与硬件不符。非代码缺陷，暂保留原样并记录在案；若要消除可把断言放宽为「无效句柄返回 null 或抛异常均可」。
